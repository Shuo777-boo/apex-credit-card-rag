# Production roadmap: 150 policies to 10 million records

The current benchmark measures 150 short policies and 30 fixed questions. It cannot establish production capacity, availability, or stable tail latency. Start production decisions with a representative, independently labeled corpus, update rate, access pattern, concurrency target and P99/error SLO. Maintain separate database and complete retrieval latency budgets: external embedding and reranking often dominate the latter.

At 10 million vectors of 1024 float32 coordinates, raw coordinates alone occupy 40.96 GB (about 38.1 GiB). Metadata, text, PostgreSQL tuple/index overhead, HNSW edges, free space, replicas and backups add materially. Measure a representative million-record shard rather than sizing RAM from coordinates alone. Batch embedding/import with bounded concurrency and backpressure, cap connection pools, monitor cache hit ratios, I/O, query plans, ANN-vs-exact recall and index rebuild time. Partition only along useful routing boundaries such as tenant/product, with separate ready ANN scopes so filters do not silently starve candidates. Add read replicas for eligible read workloads; when measured storage or rebuild/latency limits exceed PostgreSQL's operating envelope, test routed shards or an external ANN service while preserving document/version provenance. Iceberg can own versioned bulk facts and shared vectors; it does not itself provide low-latency HNSW.

Policy updates should arrive as idempotent source-version events. Validate source authorization and hashes, create a staged dataset/build, embed only changed contextualized chunks, build/analyze indexes, verify completeness and quality, then atomically switch the active version. Preserve prior builds for rollback and implement urgent withdrawals as enforced tombstones before returning evidence. Updates and deletions must propagate to ANN, graph, Iceberg snapshots and caches under one version ledger. Distinct years alone cannot establish policy supersession; effective intervals and policy lineage require authoritative source metadata.

Use separate embedding, retrieval and answer caches. Keys include normalized request, model/version/dimension, dataset/build, retrieval settings, card filter and future authorization scope. Never share a result across permission scopes. Activation, policy withdrawal and authorization changes invalidate relevant entries; short TTL is a fallback, not a correctness guarantee. Add Redis only after repeated-query rates and latency measurements justify it. Cache-hit benchmarks must be reported separately from fresh model-inclusive requests.

Before any external model call, minimize customer information and redact or tokenize PII (card/account numbers, identity documents, addresses), with a controlled re-identification boundary outside prompts. Establish supplier region, retention and data processing terms, endpoint allowlists and secrets rotation. Keep logs limited to request IDs, coarse timings and error classes, with encrypted storage, restricted access and bounded retention; avoid raw prompts/DSNs/credentials. Treat retrieved documents as untrusted data, isolate instructions from evidence, and continuously test prompt injection, wrong-card, missing-evidence and contradictory-policy cases. Citation identifier validation is not a factual guarantee; use independent human audits and structured Judge results with disclosed bias.

Production identity should use enterprise SSO plus document-level authorization applied before both dense and sparse candidate retrieval. Audit authorization decisions, document accesses, policy versions and model usage, and include permissions in every cache key. Add rate/cost quotas, circuit breakers, finite retries, protected evaluation endpoints, encrypted backups and tested restore procedures. Ship through staged canaries with regression gates for quality, model-inclusive P99, refusal behavior and error rate. The development application intentionally has no login or registration; those controls are deployment work before customer data use.
